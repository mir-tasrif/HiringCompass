# AI workflows and system prompts

The current production LangGraph workflows are chat intent classification (an initial LG1 component), job intelligence (LG2), F11 integrity and F1 requirement screening (LG3), and F2 scoring (LG4). The chat intent graph checkpoints only IDs and the selected action; existing services still execute all chat commands. The API registers LG2 at startup. The CV worker registers F11, F1 and F2 through the same graph registry, then runs each candidate's graph with its own checkpoint thread. F11 reads text already saved in a pending candidate profile, records document-integrity signals, and decides whether recruiter review is needed. Its detection rules and review policy live in `backend/app/services/f11_integrity.py`; `backend/app/graphs/lg3_screening/f11_integrity_graph.py` handles orchestration. CV extraction and profile parsing remain in `backend/app/services/cv_pipeline.py`. F1 evaluation lives in `backend/app/graphs/lg3_screening/f1_screening_graph.py` and decides whether mandatory requirements have sufficient evidence. F2 evaluation lives in `backend/app/graphs/f2_scoring/f2_scoring_graph.py`. F1 and F2 result building live in `backend/app/services/f1_screening_results.py` and `backend/app/services/f2_scoring_results.py`; the worker retains batch claiming, retry, and finalization. Shared stage history lives in `backend/app/services/cv_stage_events.py`. F5 is a transcript handoff only; F5 analysis and F6 assessment are not yet implemented.

All feature system instructions, including LG2 job intelligence, are stored in `backend/app/prompts/system.py`. LG2's prompt-building functions remain in `backend/app/graphs/lg2_job_intelligence/prompts.py`. Shared safeguards and structured-output instructions live in `backend/app/prompts/common.py`. Each catalog entry has a stable key and version. The LG1 intent, LG2 drafting, F1 screening, and F2 scoring checkpoints record their prompt versions. New parsed CV profiles, F1 screenings, and F2 scores also save the key and version with the business result; historic rows remain null because their exact prompt cannot be proven. F2's reuse hash includes its prompt version, so a revised prompt produces a new score. F11 is deterministic and records its integrity policy version instead of an LLM prompt. When changing an instruction's meaning, increment its version and retain the old text in source history. Other AI-generated business results still need persisted prompt references for complete historical explainability.

Scheduling rules such as candidate eligibility, office hours, Calendar availability and final confirmation are implemented in services; they are not LLM system prompts. Single-candidate chat scheduling is in `backend/app/services/interview_scheduling.py`; batch scheduling is in `backend/app/services/interview_chat.py`.

The next graph migration should preserve current API responses and database writes. In particular, service actions that create invitations or change candidate stages need an idempotency key before a graph node may be retried or resumed. Prompt keys and versions should be persisted with future AI results as part of that migration.
